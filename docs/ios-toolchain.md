# iOS toolchain notes

`ios/` is generated by `npx expo prebuild` and is gitignored, so everything
here lives in the repo root: a `Gemfile`, a config plugin under `plugins/`, and
`bin/ios`. This file records why each of them exists, because all three look
like clutter until you hit the failure they prevent.

The short version, from a clean clone:

```bash
npm install
bundle install
npx expo start --dev-client   # leave running
bin/ios                       # in a second shell
```

## `Gemfile` — pinning CocoaPods' dependencies

Running `pod install` against a current Ruby fails before it does any work:

```
ArgumentError - unknown keyword: quirks_mode
```

`cocoapods-core`'s gemspec pins `activesupport >= 5.0, < 8`, so CocoaPods
always resolves activesupport 7.x. That version's JSON encoder still calls
`JSON.generate(jsonified, quirks_mode: true, max_nesting: false)`, and the
`json` gem removed `quirks_mode:` in 3.0. Nothing triggers it until something
calls `#to_json` — which `expo-modules-autolinking` does on every install.
activesupport 8 dropped the call, but the CocoaPods pin puts it out of reach.

The `Gemfile` holds `json` on 2.x so the keyword still exists. Use
`bundle exec pod install`, not bare `pod install`; Expo's CLI does this for you
automatically once a `Gemfile` is present. `Gemfile.lock` is committed so
everyone resolves the same versions.

## `plugins/withPodMinimumDeploymentTarget.js` — raising pod deployment targets

Xcode 27 refuses to build any target whose `IPHONEOS_DEPLOYMENT_TARGET` is
below iOS 15. Several pods still ship *resource bundles* that declare much
older targets — SDWebImage (9.0), Sentry (11.0), ReachabilitySwift (12.0),
RNSVG's filters bundle (12.4), AsyncStorage's resources (13.4). Expo's own
`post_install` hook raises the pod targets but not their resource bundles, so a
clean `pod install` still produces a project that won't compile.

The plugin injects a `post_install` hook into the generated Podfile that raises
anything CocoaPods generates to the app's own minimum (currently 15.1, from the
`platform :ios` line).

Don't do this by passing `IPHONEOS_DEPLOYMENT_TARGET` on the `xcodebuild`
command line. That applies to every target including `AttendWidget`, whose
Live Activity code needs `ActivityViewContext` (iOS 16.1+), and the widget
stops compiling. Scoping the change to the Pods project leaves the app and
extension targets at whatever they declare.

## `bin/ios` — `expo run:ios` can't launch a simulator on Xcode 27

Xcode 27 removed the standalone `Simulator.app`; the simulator UI is now
DeviceHub (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`,
bundle id `com.apple.dt.Devices`). `@expo/cli` 54.x still resolves the
simulator by the old name in three places, so `npx expo run:ios` aborts before
it builds anything:

```
Can't determine id of Simulator app; the Simulator is most likely not
installed on this machine. Run `sudo xcode-select -s /Applications/Xcode.app`
```

That advice is a red herring. `xcode-select` is fine and `xcrun simctl` works;
`Simulator.app` simply isn't on disk any more.

There is no released fix for SDK 54. Upstream tracking:

- [expo/expo#46671](https://github.com/expo/expo/issues/46671) — the bug report
- [expo/expo#46757](https://github.com/expo/expo/pull/46757) — DeviceHub support, shipped in `@expo/cli` 56 and later
- [expo/expo#50250](https://github.com/expo/expo/pull/50250) — the SDK 54 backport, still open

`@expo/cli` 54.0.28 (the newest SDK 54 release) does not contain it. So
`bin/ios` drives the underlying tools directly — `xcodebuild`, then
`xcrun simctl install` and `simctl launch`, then opens DeviceHub so there's
something to look at. When we move to SDK 56+, `bin/ios` can go away and
`npx expo run:ios` works again.

## Troubleshooting

**`Unable to resolve module <some-package>` at the bundling step.** `node_modules`
has drifted from `package.json`. Run `npm ci`.

**`Unicode Normalization not appropriate for ASCII-8BIT` from `pod install`.**
CocoaPods unicode-normalizes the project path and Ruby reads it as binary when
the locale isn't UTF-8. Set `LANG=en_US.UTF-8` (`bin/ios` does this for you).
Usually only bites in CI and non-interactive shells.

**The app installs but shows a connection error.** The dev client needs the
bundler. Run `npx expo start --dev-client` in another shell. If port 8081 is
already taken by another checkout, pass `--port`.

**`expo prebuild` fails with `Cannot read properties of undefined (reading
'removeFromProject')`.** `@bacons/apple-targets` can't update the existing
`AttendWidget` target in place, so a second prebuild over an existing `ios/`
crashes. Use `bin/ios --clean`, or `npx expo prebuild --platform ios --clean`.
